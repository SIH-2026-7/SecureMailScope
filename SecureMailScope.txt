**Title:** SecureMailScope: AI-Assisted Cryptographic Security Posture Assessment for Secure Email Communications

## 1. Executive Proposal

**SecureMailScope** is a passive network-forensic platform that accepts email-related PCAP/PCAPNG files and produces:

- Reconstructed SMTP, IMAP, and POP3 sessions
- STARTTLS transition analysis
- TLS version, cipher suite, extension, and key-exchange analysis
- X.509 certificate extraction and validation
- Forward-secrecy assessment
- Cryptographic weakness detection
- AI-based risk classification and anomaly detection
- Security posture score
- Prioritized remediation recommendations
- Interactive dashboard
- JSON, HTML, and PDF forensic reports

The core differentiator is that SecureMailScope does not merely show packets. It converts raw packet evidence into an explainable security decision:

> “This email service is vulnerable because STARTTLS was advertised but not enforced, TLS 1.0 was negotiated, the server certificate is expired, and the session lacks forward secrecy. Remediate in this order.”

NIST TLS guidance emphasizes TLS 1.2 with approved cipher suites and migration toward TLS 1.3, while RFC 8314 recommends TLS 1.2 or greater for email submission and access, discourages cleartext email protocols, and prefers implicit TLS for submission and access services. ([csrc.nist.gov](https://csrc.nist.gov/Pubs/sp/800/52/r2/Final?utm_source=openai))

# 3. End-to-End Processing Pipeline

## Stage 1: PCAP Intake

The user uploads a `.pcap`, `.pcapng`, or compressed capture.

Validation checks:

- File extension and magic bytes
- Maximum file size
- PCAP readability
- Packet count
- Capture start and end time
- Link-layer type
- Presence of TCP traffic
- SHA-256 evidence hash

Every analysis should store:

```json
{
  "evidence_id": "pcap-2026-001",
  "file_name": "enterprise-mail.pcapng",
  "sha256": "....",
  "capture_start": "2026-08-12T10:00:00Z",
  "capture_end": "2026-08-12T10:12:24Z",
  "packet_count": 182340,
  "analyzer_version": "1.0.0"
}
```

The evidence hash gives the forensic report integrity and supports chain-of-custody verification.

## Stage 2: Protocol Identification

Identify candidate email sessions using:

### Port-based detection

| Protocol | Cleartext / STARTTLS | Implicit TLS |
|---|---:|---:|
| SMTP | 25, 587 | 465 |
| IMAP | 143 | 993 |
| POP3 | 110 | 995 |

### Content-based detection

Port numbers alone are insufficient. Use application signatures:

#### SMTP

```text
220 mail.example.com ESMTP
EHLO client.example.com
250-STARTTLS
STARTTLS
220 Ready to start TLS
```

#### IMAP

```text
* OK IMAP4rev1 Service Ready
A001 CAPABILITY
* CAPABILITY IMAP4rev1 STARTTLS AUTH=PLAIN
A002 STARTTLS
A002 OK Begin TLS negotiation now
```

#### POP3

```text
+OK POP3 server ready
STLS
+OK Begin TLS negotiation now
```

### Confidence model

```text
protocol_confidence =
    0.35 * port_match +
    0.35 * banner_match +
    0.20 * command_sequence_match +
    0.10 * tls_context_match
```

The detector should output `SMTP`, `IMAP`, `POP3`, or `UNKNOWN`, together with an evidence explanation.

## Stage 3: TCP Stream Reconstruction

For every TCP 5-tuple:

```text
(source_ip, source_port, destination_ip, destination_port, protocol)
```

perform:

1. SYN/SYN-ACK/ACK identification
2. Direction assignment
3. TCP sequence-number ordering
4. Retransmission removal
5. Duplicate segment removal
6. Out-of-order segment buffering
7. Gap detection
8. FIN/RST session termination detection
9. Stream byte reconstruction

Output:

```json
{
  "stream_id": 42,
  "client": "10.10.1.25:50214",
  "server": "10.10.2.10:587",
  "protocol": "SMTP",
  "bytes_client_to_server": 1842,
  "bytes_server_to_client": 2380,
  "retransmissions": 4,
  "missing_bytes": false,
  "start_time": "...",
  "end_time": "..."
}
```

### Important forensic limitation

A PCAP may be incomplete. If packets are missing, the system must not silently claim that a handshake or certificate is valid. It should mark evidence quality as:

- `COMPLETE`
- `PARTIAL`
- `TRUNCATED`
- `AMBIGUOUS`

## Stage 4: STARTTLS Detection and Validation

STARTTLS must be treated as a state transition.

```text
PLAINTEXT
    |
    | capability advertised
    v
STARTTLS_AVAILABLE
    |
    | client sends STARTTLS/STLS
    v
UPGRADE_REQUESTED
    |
    | server accepts
    v
TLS_EXPECTED
    |
    | TLS ClientHello detected
    v
ENCRYPTED
```

### SMTP validation rules

RFC 3207 defines SMTP STARTTLS and requires the client to begin TLS negotiation after receiving a successful `220` response. ([rfc-editor.org](https://www.rfc-editor.org/rfc/rfc3207.html?utm_source=openai))

SecureMailScope should detect:

| Finding | Condition |
|---|---|
| STARTTLS not offered | Server banner/capability lacks STARTTLS |
| STARTTLS offered but unused | Capability advertised, client continues cleartext |
| STARTTLS rejected | Server returns `454` or another failure response |
| STARTTLS downgrade suspicion | One endpoint previously offered STARTTLS but later sessions do not |
| TLS handshake missing | Server accepts STARTTLS but no ClientHello follows |
| Cleartext authentication | Credentials or authentication commands observed before encryption |
| Post-upgrade cleartext | Application commands appear after TLS transition outside expected boundaries |

For IMAP, analyze `CAPABILITY` and `STARTTLS`.  
For POP3, analyze `STLS` and the server response.

### Critical security insight

The system must distinguish:

```text
STARTTLS available
```

from:

```text
STARTTLS successfully negotiated and subsequently used
```

This distinction is central to downgrade and opportunistic-encryption analysis.

# 4. Certificate Analysis

## Certificate checks

### Identity validation

- Does the certificate SAN match observed SNI?
- Is the certificate issued for the observed server name?
- Is the certificate self-signed?
- Is the certificate chain complete?
- Is the issuer trusted by the configured trust store?

### Time validation

```text
not_before <= capture_time <= not_after
```

Findings:

- Expired certificate
- Certificate not yet valid
- Certificate expires soon
- Excessively long validity period
- Invalid validity ordering

### Cryptographic validation

Flag:

- RSA key below 2048 bits
- DSA certificates
- EC keys using weak curves
- SHA-1 signatures
- MD5 signatures
- Unknown or unsupported algorithms
- Weak certificate signature chains

### Chain validation

The platform should report separate states:

```text
CHAIN_PRESENT
CHAIN_COMPLETE
CHAIN_SIGNATURE_VALID
CHAIN_TRUSTED
IDENTITY_MATCHED
TIME_VALID
```

Do not collapse these into a single “valid/invalid” value.

### Offline analysis limitation

A passive PCAP-based system can validate certificates using the certificate chain present in the capture and a local trust store. It cannot reliably prove real-time revocation status unless OCSP/CRL traffic or an authorized online validation service is available. The report should explicitly label revocation as:

- `VALIDATED`
- `NOT_OBSERVED`
- `NOT_CHECKED_OFFLINE`
- `REVOKED`

This makes the product more trustworthy than tools that overclaim certificate validation.

# 5. Cryptographic Weakness Rules

## TLS version rules

| TLS version | Severity |
|---|---|
| SSLv2 / SSLv3 | Critical |
| TLS 1.0 | High |
| TLS 1.1 | High |
| TLS 1.2 | Acceptable with strong configuration |
| TLS 1.3 | Recommended |

RFC 8314 recommends TLS 1.2 or greater for email submission and access and prefers implicit TLS for these services. ([rfc-editor.org](https://www.rfc-editor.org/rfc/rfc8314.html?utm_source=openai))

## Cipher suite rules

### Critical or high-risk

- NULL encryption
- Anonymous authentication
- Export-grade cipher suites
- RC4
- DES
- 3DES
- MD5
- Static RSA key exchange
- CBC-only suites where policy disallows them
- Weak or unknown cipher suites

### Recommended

TLS 1.2:

```text
ECDHE_RSA_WITH_AES_128_GCM_SHA256
ECDHE_RSA_WITH_AES_256_GCM_SHA384
ECDHE_ECDSA_WITH_AES_128_GCM_SHA256
ECDHE_ECDSA_WITH_AES_256_GCM_SHA384
```

TLS 1.3:

```text
TLS_AES_128_GCM_SHA256
TLS_AES_256_GCM_SHA384
TLS_CHACHA20_POLY1305_SHA256
```

### TLS 1.3 implementation detail

In TLS 1.3, the cipher suite does not fully describe the key-exchange mechanism. SecureMailScope must inspect `supported_groups` and `key_share` extensions to assess the negotiated group and forward secrecy.

## Forward secrecy rules

```text
forward_secrecy = true
```

when the session uses:

- ECDHE
- DHE
- TLS 1.3 ephemeral key exchange

```text
forward_secrecy = false
```

when the session uses:

- Static RSA key exchange
- Anonymous or unknown key exchange
- Incomplete handshake evidence

Use Isolation Forest for the first version.

Train primarily on known-good sessions and identify:

- Rare cipher selection
- Unexpected TLS version changes

- Server identity changes
- Certificate fingerprint changes
- Unusual extension combinations
- STARTTLS behavior inconsistent with the baseline

Every AI decision should include:

- Evidence packet numbers

Avoid using a generative AI model to invent vulnerabilities. If an LLM is added, use it only to summarize structured findings and generate remediation language from a controlled knowledge base.

# 11. Analysis Worker Flow

```python
def analyze_capture(capture_path: str, capture_id: str) -> dict:
    evidence = validate_capture(capture_path)

    packets = tshark_extract_packets(capture_path)

    tcp_streams = reconstruct_tcp_streams(packets)

    sessions = []

    for stream in tcp_streams:
        protocol = identify_email_protocol(stream)

        if protocol not in {"SMTP", "IMAP", "POP3"}:
            continue

        application_state = detect_email_state_machine(
            stream,
            protocol=protocol
        )

        tls_handshake = parse_tls_handshake(stream)

        certificates = extract_certificates(tls_handshake)

        certificate_results = validate_certificates(
            certificates,
            observed_sni=tls_handshake.sni,
            capture_time=stream.start_time
        )

        crypto_findings = evaluate_crypto_posture(
            protocol=protocol,
            application_state=application_state,
            tls=tls_handshake,
            certificates=certificate_results
        )

        feature_vector = build_feature_vector(
            stream=stream,
            protocol=protocol,
            application_state=application_state,
            tls=tls_handshake,
            certificates=certificate_results
        )

        ai_result = classify_and_detect_anomaly(feature_vector)

        findings = merge_rule_and_ai_findings(
            crypto_findings,
            ai_result
        )

        score = calculate_posture_score(findings)

        sessions.append({
            "protocol": protocol,
            "tls": tls_handshake,
            "certificates": certificate_results,
            "findings": findings,
            "score": score,
            "evidence_quality": assess_evidence_quality(stream)
        })

    report = build_report(
        capture_id=capture_id,
        evidence=evidence,
        sessions=sessions
    )

    persist_report(report)

    return report
```

# 12. Rule Engine

Use versioned rules instead of hard-coded scattered conditions.

```yaml
rules:
  - id: TLS-001
    title: Deprecated TLS version
    severity: high
    when:
      field: negotiated_version
      in:
        - TLSv1.0
        - TLSv1.1
    impact: >
      The session uses a deprecated TLS protocol version with
      reduced cryptographic assurance.
    recommendation: >
      Disable TLS 1.0 and TLS 1.1. Require TLS 1.2 or TLS 1.3.

  - id: CERT-001
    title: Certificate expired
    severity: high
    when:
      field: certificate.expired
      equals: true
    impact: >
      Certificate validity cannot be established at capture time.
    recommendation: >
      Replace the certificate and deploy automated renewal monitoring.

  - id: SMTP-001
    title: STARTTLS advertised but not used
    severity: high
    when:
      all:
        - field: starttls_advertised
          equals: true
        - field: starttls_used
          equals: false
    impact: >
      The connection remained in cleartext despite TLS upgrade support.
    recommendation: >
      Enforce TLS on submission and access services and reject
      authentication before encryption.

  - id: TLS-002
    title: No forward secrecy
    severity: medium
    when:
      field: forward_secrecy
      equals: false
    impact: >
      Captured traffic may be exposed if the server private key is
      compromised in the future.
    recommendation: >
      Prefer ECDHE, DHE, or TLS 1.3 cipher suites.
```

# 17. Security and Privacy Controls

Because PCAP files can contain credentials, message metadata, and sensitive enterprise traffic:

- Run all analysis locally or in an isolated deployment
- Never upload PCAP files to public AI services
- Redact email addresses where possible
- Do not reconstruct or display message bodies by default
- Hash identifiers in the dashboard
- Encrypt stored evidence
- Apply role-based access control
- Log analyst actions
- Use read-only evidence storage
- Sandbox TShark and parser processes
- Enforce upload size and execution time limits
- Delete temporary extracted streams after processing
- Prevent command injection in file paths
- Validate all generated report fields
- Avoid logging raw packet payloads

For the AI component:

- Use structured feature input
- Version the model and training dataset
- Validate predictions against deterministic rules
- Require analyst review for critical conclusions
- Record model version and feature values
- Test resistance to poisoned or malformed input

OWASP guidance emphasizes data provenance, anomaly detection, model monitoring, and human oversight for AI-enabled security systems. ([cheatsheetseries.owasp.org](https://cheatsheetseries.owasp.org/cheatsheets/Secure_AI_Model_Ops_Cheat_Sheet.html?utm_source=openai))
